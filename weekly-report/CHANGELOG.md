## 2026-08-27 — defensible-wording-and-quote-numbering-trap

对照用户 0817-0821 周的编辑沉淀，两处改动：

- **4.1 新增「问题陈述要用可辩护的措辞，不要用绝对化断言」**。周报是拿到会上讲的，一句话被反问顶回来整段可信度都掉。用三行表钉住三类绝对化写法及改法：能力全无（「Agent 和文件树都**看不见**」→「**不方便查阅**」）、结果全无（「也**留不下来**」→「也**不容易**留下来」）、极值断言（「**用得最深的那批人**迁移成本**反而最高**」→ 删掉或改成程度描述）。另补一类**范围越界**：把还没谈定的范围写进推广目标（「推广至全商业平台**与互部**」），范围只写已有依据的那一层。自检方法：每个判断句问一遍「有没有显而易见的反例」，有就降级。并说明降级不削弱说服力——机制描述本身足够有力，绝对化只是虚张声势。
- **5.2 坑清单从 5 条扩到 6 条**，新增：引用块里的子项不要带 markdown 编号。写 `   > 1. **xxx**：说明` 时转换器可能把它识别成有序列表项（`block_type=13`）而非引用（`block_type=15`），导致子项与主编号点落进同一个列表、编号从 1 串到十几，主次层级看不出来；同一篇文档里这个行为还不稳定。对策是子项去掉 `1. 2. 3.` 直接写 `   > **粗体短语**：说明`，连续多行会正确合并成一个引用块；校验时看 `docx blocks` 的 `block_type`（主点 13、子项 15）。

## 2026-08-09 — problem-for-inflight-work-and-feishu-write-traps

## 2026-08-02 — data-composition-and-noise-removal

对照用户 0727-0731 周的定稿与 AI 草稿的差异沉淀，四处改动：

- **阶段 3 新增反问 2b「拿到数字之后必须追问构成」**。这是本次最大的漏点：AI 采访三轮只拿到「累计注册 240 人」，从没问过这 240 人是谁。用户定稿补上了「涉及销售、参谋部、综管等非研发部门，并扩散到汽车部、技术委、中国区、信息部」，数字才从平淡变成硬证据。规则明确：总量只回答「多少」，构成才回答「这个多少说不说明问题」；同样适用于调用量（谁在调）、收入（哪些客户）、覆盖率（没覆盖的是哪一类）。
- **4.2 修正顶层写法**：顶层写的是结果本身，不是对结果的评论，也不是「本周分几块讲」的框架句。用三行对照表钉死两个实际犯过的反例——旁白式（"这一行第一次拿出使用数据"，在评论周报自身历史）和框架句式（"本周主线从 A 转到 B"）。补充自检法：念给只关心业务的人听，他问「所以呢」说明写成了评论，问「哪些人」说明数据缺构成。
- **4.2 新增「概括分类时要留一个最可感的具体实例」**：把能力归到分类名下会吞掉最有画面感的那条（"移动端优化"吞掉了"支持 iOS/Android 原生手机通知"）。举 bug 例子也要选读者能想象出画面的。
- **新增 5.-2「交付前先删掉不该在周报里的东西」**：五类噪音——自己的工作过程（"已对着源码逐条校验"）、技术口径式免责说明、单个 issue 粒度的细节、没有交付物的计划条目（"持续跟踪"/"持续观察"）、内部机制的自我指涉。口径与依据降级到引用块，正文只留结果。
- 同步在 `~/.rollie/weekly_report/learnings.md` 新增一条**有范围**的条目，记录这份周报「项目进展/风险」单元格的三层结构与粒度偏好（不升级进正文）。

## 2026-07-26 — feishu-cli-and-red-bold-emphasis

- 新增 **5.0 重点标记**规则：周报靠「标红加粗」承载会上要直接讲的重点。飞书文档用标红+加粗，本地 Markdown 只能加粗（无颜色语法，不要伪造 `<span style>`）。明确该标什么（金字塔顶层结论、第二层判断短语、关键量化数字、本周承诺动作）以及不要整段标红。
- **重写 5.2 飞书输出章节**：原内容引用 `mcporter` / `create-doc` / `fetch-doc` 这套已废弃的 MCP 调用，改为现行 `feishu` CLI（`feishu docx create -f` / `feishu docx update --mode replace --select-title`）。
- 记录三个已实测验证的坑：
  1. `feishu docx color-text` 不解析 `**bold**`，会留下字面 `**` 且 `bold: false`，不能用于「标红+加粗」；
  2. `feishu fetch` 返回的 markdown 不序列化颜色，用它校验标红会产生假阴性；
  3. `feishu docx create` 返回 `fallback: true` 不代表颜色写入失败。
- 明确唯一可信的校验方式：`feishu docx blocks` 读回 `text_element_style.text_color`（红=1）与 `bold`，并检查无残留字面 `**`。
- 正确写法固定为颜色标签在外、加粗在内：`<text color="red">**...**</text>`。
