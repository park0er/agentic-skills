# 交接文档模板

下面是 `HANDOFF.md` 的推荐章节结构。按实际情况裁剪,但**第四节(真实状态)和第五节(下一步是候选项)不可省**。每节方括号是填写说明,产出时替换为实际内容。

```markdown
# Handoff:<主题一句话>

> 冷启动交接文档 · <日期> · 给接手的 agent 看
> 目的:让你在没有前序对话上下文的情况下,理解这块在干什么、做到哪、接下来可能做什么。**这是背景交接,不是派活清单**。

## 一、项目背景
[这是什么项目/任务,为什么做,核心目标一两段说清。假设读者零上下文。]

### 关键资料位置
| 资料 | 位置 |
|---|---|
| [源码/主文件] | [绝对路径] |
| [关键文档] | [绝对路径] |
| [外部资料] | [链接 + 如何访问,如"读飞书用 feishu fetch,不要 web_fetch"] |

## 二、当前理解 / 已建立的认知
[对问题域、现有系统、关键概念的理解。让接手者不必重新摸索。]

## 三、本轮产出(已完成)
[列出已交付的东西:文件、链接、资源 id。每项给位置 + 一句话说明它是什么、核心结论。]

## 四、真实状态:动过什么 / 没动什么 ⚠️必填
[逐一说明每个被触碰对象现在的状态:]
- [X 已改:改了什么]
- [Y 未动:保持原样]
- [Z 改动已回滚:现与动手前一致]
> 接手须知:[如"除非用户明确要求,不要改 <某 skill/文件>"。若发生过越界改动并回滚,在此写明教训。]
> 环境怪癖:[如"<目录> 不是 git 仓库,改动不可靠 git 回滚";"<CLI> 已认证"等。]

## 五、可能的下一步(待用户决定,勿擅自执行)⚠️必填
[这些是候选项,不是任务。等用户拍板:]
1. [候选项 1]
2. [候选项 2]

## 六、环境 / 工具备注
[复现工作所需的工具用法、命令、认证、资源 id 等。]
```

## 填写要点

- **真实状态节**用工具实际核实,不靠记忆。把"已改/未动/已回滚"分清。
- **下一步节**全部标注待定;命令式动词只能出现在"如果用户要 X → 则做 Y"的条件句里,不能是裸指令。
- **资料位置**一律给绝对路径、完整链接、资源 id;能复制即用。
- 通篇语气是**陈述现状**,不是**下达任务**。
