# 召回链路业务指南

纯业务知识，不涉及看板操作。如需查看字段定义和查询方法，请参考：
→ references/xirang_recall_diagnosis_field_dictionary.md

## 链路总览

```
下发 → 进入召回 → 召回前过滤 → 多路召回 → merge层 → 业务过滤/TopN → 出召回 → 粗排
```

召回链路是广告引擎的第一道筛选，负责从海量候选广告中初步筛选出可能相关的候选集。

## 一、进入召回

漏斗顶端，所有进入召回环节的广告候选量。

这是召回环节的入口，上游下发后的全部候选广告都在这里。

## 二、召回前过滤（commonProcess）

进入召回后、多路召回前，对候选广告进行统一初步筛选，减少后续召回的计算量。

**过滤类型**：

- **索引过滤**：基于倒排索引的快速筛选
- **RTA过滤**：基于实时接口的过滤
- **流量优选**：基于流量质量的筛选

这一层是统一的，所有候选广告都会经过。过滤后的量级直接影响后续召回的效果。

## 三、多路召回

召回前过滤之后，从不同角度召回可能相关的广告。

**通路类型**：

| 通路 | 说明 | 优先级 |
|---|---|---|
| 白名单类（white/ecp） | 人工配置的高优先级广告 | 最高 |
| 策略通路（fresh/提价） | 解决特定业务问题 | 中 |
| 模型通路（ann/llm） | 算法召回 | 最低 |

**并发逻辑**：一个请求会同时进入多条通路并行召回，每条通路独立运行、互不影响。同一个广告可能在多条通路中都被召回，因此会存在重复计数的情况。

**Q: 各个通路下的processor是什么？**
→ 通路内的过滤项，不符合该业务通路门槛或筛选逻辑的部分会被过滤掉。

## 四、merge 层

多路召回之后，对各通路候选广告做统一资源分配。

**工作原理**：各通路独立召回，可能重复或冲突。merge 层按业务优先级 zigzag 取数，边取边去重，保证进入粗排的 adid 既覆盖关键业务诉求，又不会被单一通路挤占。

**类比 🍉 团建分水果**：HR、行政、财务几个部门（= 各通路）同时往果盘里送自己爱吃的。切果盘的人（= merge 层）按提前说好的比例，每次从每个部门的果堆里轮流取几块（zigzag），最后拼出的果盘既有西瓜也有葡萄，不会因为某部门送得多就全是一种水果。

**Q: 哪些位置接了 merge 层？**
→ 目前全媒体推荐位置都已接 merge 层，搜索还没有。

## 五、业务过滤与 TopN

merge 层之后，进行最后的业务规则筛选。

- **业务过滤**：基于业务规则的筛选（如频控、预算等）
- **TopN**：只保留排名前 N 的候选广告

有了 merge 层后，会小时级动态调控出 merge 层的量，TopN 触发情况已缓解很多。

## 六、出召回

漏斗底端，最终进入粗排的候选广告量，是召回环节的最终输出，后续由粗排环节继续筛选。
