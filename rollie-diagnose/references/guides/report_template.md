# 报告模板与规范

最终报告必须是结构化 Markdown，并且证据要充分，不能只写结论。

## 报告结构

最终报告至少包含以下部分，顺序不要乱：

1. 诊断报告头部
2. 总结快照（Summary Dashboard）
3. 阶段一时间趋势分析结论 + 下钻证据
4. 阶段二漏斗证据
5. 最终根因结论与问题链条
6. L1 / L2 / L3 建议
7. 本次执行日志

## 诊断报告头部

报告开头用一张简洁的元信息表，固定字段如下：

| 字段          | 说明                                     |
| ----------- | -------------------------------------- |
| 发起时间        | 本次诊断的执行开始时间戳（格式：`YYYY-MM-DD HH:mm:ss`） |
| 数据窗口        | 用户指定的异常时间段（起止日期/小时）                    |
| 对比窗口        | 对比期（如有），否则写"无"                         |
| session_id | 本次会话 ID                                |

禁止用"诊断时间"这个模糊标签，它不能区分"执行时刻"和"数据窗口"。

## 总结快照（Summary Dashboard）

这是给运营先看的高密度摘要，必须放在详细证据之前。至少包含：

1. 计划整体表现
2. Top 掉量广告
3. 掉量位置（tagId / 流量位）
4. 漏斗状态一览表
5. 一句话根因
6. 一句话版 L1 / L2 / L3 建议

这里可以使用 Markdown 表格，不要只写纯文字。

## 报告必须包含的内容

1. 摘要放在最前面
2. 阶段一必须写出时间趋势分析结论：各时段是正常还是异常、是否收窄了时间窗口及原因（如跳过了 Step 2 也要说明）
3. 阶段一必须写出你比较过哪些 `campaignId / adId / tagId`
4. 阶段二必须逐环节写结论：正常 / 异常 / 无数据
5. 每个关键结论都要写 `current vs comparison (change%)`
6. 如果用了过滤码知识库，要把查到的含义和建议写进证据链
7. 必须有"漏斗状态一览表"，汇总每个节点是正常 / 异常 / 无数据
8. 必须有"最终根因结论"，明确写出问题链条
9. 报告底部必须附"本次执行日志"

## 分级建议怎么写

`L1 / L2 / L3` 不是三个空标签，它们分别代表不同责任层级和不同可执行动作：

1. `L1（广告主/优化师可操作）`
   这一层写用户现在就能做的动作，例如：
   - 调价
   - 换素材
   - 放宽定向
   - 调整预算或出价策略
2. `L2（内部运营侧接入）`
   这一层写需要平台运营或内部同学跟进的动作，例如：
   - 加系数提价
   - 加白名单
   - 跟进特定过滤项
   - 跟进异常的数字型 `sFilerReason`
3. `L3（研发介入）`
   这一层写需要研发或系统团队介入的问题，例如：
   - 模型偏差、超时
   - 索引异常
   - 调价逻辑异常
   - 看板字段或系统链路问题

## 分级建议填写规则

1. 每一条建议都必须能在前文证据里找到依据
2. 不要写与本次排查无关的通用建议
3. 如果没有足够证据支撑某一级，就不要硬写
4. 对 `sFilerReason` 这类数字码，可以映射一下实际含义，不要编造原因

## 报告风格

1. 先结论，后证据
2. 证据要足够多，能服众
3. 不能只给一行结论
4. 不能只贴原始 JSON
5. 不要中途停下来问用户是否继续

## 本次执行日志

报告最下方必须追加执行日志，格式严格如下：

**首行（汇总行）**：

```
[总计] N 轮调用 | 总耗时 Xs | 成功 N / 空数据 N / 错误 N
```

**逐轮记录**（每轮一行，格式固定）：

```
[#N] <工具名> | 耗时 Xs | <状态: 成功/空数据/错误>
     → 查询参数: adId=xxx, tagId=xxx, start=xxx, end=xxx, group_by=xxx（只列非默认参数，不要复制完整 JSON）
     → 返回摘要: 共 N 行, 关键值: xxx=N, change=±N%（或"空"/"报错信息"）
```

规则：

1. `查询参数` 行只写关键非默认参数，不要粘贴完整 JSON
2. `返回摘要` 行只写结果的基础信息（行数、核心指标变化），不要复述分析
3. 耗时标签必须写在状态前，格式 `耗时 Xs`，不允许模糊写法如"很快""较慢"
4. 如果某轮调用状态为"错误"，必须在返回摘要里写错误 code 或 message

这部分的目的是让人能回看"你到底查了什么、参数是什么、返回了什么"。
